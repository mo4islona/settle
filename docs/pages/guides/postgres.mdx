# Write changes to Postgres [Apply each batch in one transaction and survive a crash at any point]

<LanguageSwitch label="Code language" />

Settle calculates your tables, but it does not answer queries. Your app writes the changes to a database, and reads the data from there. This guide uses Postgres. The same method works for each database that has transactions.

The method has three rules:

- Apply each batch in **one transaction**.
- Store the **sequence number** of the batch in the same transaction.
- Call `ack` **after** the commit.

Then your database and Settle agree after each crash, also after a crash between the commit and the ack.

You need a Postgres server and a Postgres client library:

:::code-group

```bash [TypeScript]
npm install @settle/stream pg
npm install --save-dev tsx @types/pg
```

```bash [Rust]
cargo add settle --git https://github.com/mo4islona/settle
cargo add postgres@0.19
```

:::

## Test a crash

Run the example three times. The second run stops after Postgres commits batch 4, but before the ack:

:::code-group

```bash [TypeScript]
export DATABASE_URL=postgres://postgres:postgres@127.0.0.1:5432/postgres
npx tsx postgres.ts
npx tsx postgres.ts --crash
npx tsx postgres.ts
```

```bash [Rust]
export DATABASE_URL=postgres://postgres:postgres@127.0.0.1:5432/postgres
cargo run --release --bin postgres
cargo run --release --bin postgres -- --crash
cargo run --release --bin postgres
```

:::

:::code-group

```ansi [TypeScript]
continue after: null
sequence in Postgres: 3
[
  { pool: 'BTC/USDC', volume: 200, swaps: 2 },
  { pool: 'ETH/USDC', volume: 100, swaps: 1 }
]
continue after: { number: 3, hash: '0x3' }
batch 4 is in Postgres, stop before the ack
continue after: { number: 4, hash: '0x4' }
sequence in Postgres: 7
[
  { pool: 'BTC/USDC', volume: 400, swaps: 4 },
  { pool: 'ETH/USDC', volume: 300, swaps: 3 }
]
```

```ansi [Rust]
continue after: None
sequence in Postgres: 3
{ pool: BTC/USDC, volume: 200, swaps: 2 }
{ pool: ETH/USDC, volume: 100, swaps: 1 }
continue after: Some(BlockCursor { number: 3, hash: "0x3" })
batch 4 is in Postgres, stop before the ack
continue after: Some(BlockCursor { number: 4, hash: "0x4" })
sequence in Postgres: 7
{ pool: BTC/USDC, volume: 400, swaps: 4 }
{ pool: ETH/USDC, volume: 300, swaps: 3 }
```

:::

Settle did not get the ack of batch 4. But Postgres has sequence 4, so the third run opens Settle after block 4. Settle does not give batch 4 again, and the totals for blocks 1 to 7 are correct.

## Why store the sequence number

Without the applied sequence, Settle opens at the last batch with an ack. In the test above, it continues after block 3 and gives batch 4 again. The upsert writes the same values again, so the result stays correct.

But the chain can replace block 4 before your app sends it again. Then Settle does not know that Postgres has the changes of block 4, and it cannot undo them. The sequence number in Postgres closes this gap.

[Restarts and crash safety](/guides/restarts) explains the start errors when the two stores do not agree.

## Write the raw rows too

The tables in this guide are virtual: Settle sends only the view rows. To also keep the raw rows in Postgres, make the table not virtual. Then each batch also has records for the table:

- The key of a raw row is `block_number` and `_row_index`, the position of the row in its block.
- An insert gives the columns of the row in its values.
- After a fork, a delete removes each row of the replaced blocks.

Use `(block_number, _row_index)` as the primary key of the Postgres table.
